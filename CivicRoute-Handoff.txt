Updated: 2026-10-30 (Asia/Calcutta)

PURPOSE
-------
CivicRoute is a Karnataka public-service navigator. The backend identifies a
requested government service, uses trusted/reviewed data as the authority,
explains steps in plain language, and can locate explicitly authorized service
centres. The catalogue is intended to expand by data, across departments and
public-service categories. Do not interpret the current sample journey IDs as
the complete product scope.

API CONTRACTS AND INTEGRATION
============================
GET /health
  Returns a minimal status object: {"status":"ok"}. It does not expose config,
  local paths, prompts or credentials.

POST /ask request
  {"question":"I need an income certificate","language":"en"}
  Supported fields are question (nonblank, max 2,000 chars) and language
  ("en" or "kn", default "en"). Extra request fields are rejected. The
  frontend /ask payload remains question + language; do not add location to
  that request without a separately agreed contract change.

POST /ask response
  The current contract supports an "ok" response with service_id,
  service_name, language, steps, structured documents, fee, online_option,
  office_type, grievance, sources, last_verified and warnings. Unsupported
  responses have status="unsupported", service_id="unknown", service_name=null,
  message, official_portal_url (only if verified/configured),
  suggested_services and warnings. A clarification_needed response is also
  supported by the existing frontend. See backend/schemas.py and README.md for
  exact current models. Do not change /ask while integrating centres.

GET /centres (added 2026-10-30)
  Query: service_id (required); district, taluk, or area (optional); latitude
  and longitude (optional but must be paired); max_results (1..50, default 20).
  The frontend uses the existing district-or-taluk input as `area`. It asks
  browser geolocation only after the user selects “Use my location to show
  distance”. Response:
  {"service_id":"...","centres":[{"id":null,"name":"...",
  "centre_type":"...","address":"...","district":"...","taluk":"...",
  "latitude":null,"longitude":null,"service_capabilities":[...],
  "sources":[...],"last_verified":"YYYY-MM-DD","distance_km":null}]}
  Exact optional values depend on the promoted record. The route returns only
  known trusted service IDs and centres whose status is verified, verification
  date is not future/older than 365 days, dated source provenance exists, and
  requested-service capability is explicitly verified and has source URLs.
  Nearby status never implies authorization. Centres lacking coordinates may
  be included without distance unless coordinates were requested for distance
  ordering. Invalid service IDs are rejected; unlisted service IDs return 404.

The map component loads Google Maps only when the existing Find Nearby Centres
button reveals it. Markers are created only from /centres results with
coordinates; details include the centre and source/verification information.
The existing VITE_GOOGLE_MAPS_API_KEY remains frontend/browser configuration
only. Do not add backend Gemini or search keys to frontend environment.

TRUST, SECURITY, AND PRODUCT DECISIONS
======================================
- Trusted bundled service data is authoritative. The LLM can classify or
  rephrase verified steps only; Python/Pydantic validate model output.
- The deterministic intent classifier remains the fallback when Gemini is
  absent or fails. Accepted IDs currently include aadhaar_update,
  income_certificate, civic_complaint, with unknown for out-of-scope/unclear
  requests. Catalogue records and aliases are data-driven and expandable.
- Missing/unverified fees stay null/not_verified; document statuses such as
  required, conditional and commonly_requested remain distinct.
- Official-source results are discoveries, not trusted facts. They preserve
  provenance and remain in the review workflow until manual review and
  separately approved promotion.
- Bundle imports are JSON schema version 1; validation reports malformed,
  duplicate, conflicting, stale and provenance-incomplete records. Promotion
  requires explicit record approval, reviewer and note; writes use backup and
  atomic replacement. Never promote test fixtures or pending discoveries.
- Centre authorization must be explicit and source-backed. No coordinates,
  offices, fees, documents, eligibility or government facts may be fabricated.
- Backend settings read GEMINI_API_KEY, GEMINI_MODEL, LOG_LEVEL, CORS_ORIGINS,
  CIVICROUTE_VERIFIED_GENERAL_PORTAL_URL, OFFICIAL_SOURCE_PROVIDER,
  BRAVE_SEARCH_API_KEY and OFFICIAL_SOURCE_APPROVED_HOSTS. Values are not
  recorded here. Gemini/live search remain optional/configuration-dependent.
- Frontend environment names include VITE_API_BASE_URL and
  VITE_GOOGLE_MAPS_API_KEY. Values are not recorded here. Production CORS must
  be restricted to explicit deployed frontend origins; no wildcard with
  credentials.
- No authentication, accounts, application submission, database, request
  history persistence, or additional service journeys were added.
